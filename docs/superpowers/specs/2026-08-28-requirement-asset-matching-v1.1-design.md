# 项目需求与历史资产数据匹配重构设计 v1.1

> 状态：已批准设计，待实施计划
>
> 批准日期：2026-08-28
>
> 适用范围：项目管理需求与资产中心历史数据匹配、需求分析 Agent 的需求匹配能力

## 1. 背景

当前项目存在两条需求匹配链路：

- 项目管理链路以向量相似度、词法分数和通用模型评分生成匹配结果，并可能依据分数自动关联资产、修改需求状态。
- 需求分析 Agent 链路已经包含 Dense、FTS5/BM25、RRF、CrossEncoder、确定性评分和可选模型解释，但没有被项目管理链路统一复用。

两条链路的召回、评分、失败处理和业务写入权限不一致。现有匹配结果还混合了排序依据、语义结论和业务状态，导致百分比分数容易被误解为准确率，并可能直接改变业务事实。

本次重构统一两条链路，同时保留根据项目需求内容自动检索历史需求数据、计算综合匹配分并按匹配程度排序的核心能力。重构限制的是未经确认的自动业务写入，不是自动匹配和自动排序。

## 2. 设计目标

1. 项目管理和需求分析 Agent 使用同一个匹配核心与同一套候选结果契约。
2. 系统根据项目需求内容自动检索资产中心历史数据，并按综合匹配程度生成稳定的 Top N 排序。
3. 分离语义关系、决策状态、证据等级、排序分和业务关联状态。
4. 精确、确定性的重复记录可以被系统确认；语义模型结果只作为建议。
5. 模型或解释服务失败时采用封闭失败策略，不产生资产关联或需求状态写入。
6. 每次匹配运行都可追溯、可复现、可比较，历史运行不可被覆盖。
7. 在不建设人工评测集的前提下，通过确定性事实、变形测试、安全不变量和性能基线建立自动化发布门禁。

## 3. 非目标

- 不根据语义匹配分自动建立正式资产关联。
- 不根据语义匹配分自动将需求设置为“已满足”。
- 不把综合匹配分解释为统计概率、置信概率或真实业务准确率。
- 不使用模型共识、合成改写或历史未知来源关联证明真实业务准确率。
- 本阶段不引入 ANN 或分布式向量基础设施。
- 本阶段不重构与需求匹配无关的项目管理、资产中心或 AI 助手功能。

## 4. 方案选择

### 4.1 可选路线

1. **最小修补**：让项目管理直接调用现有 Agent 匹配链路。改动较小，但无法解决旧结果覆盖、业务写入权限和评分语义问题。
2. **统一匹配核心与确定性决策策略**：统一召回、重排、证据和决策，模型只负责排序增强、建议关系和解释。该路线为本设计采用方案。
3. **完全确定性规则**：最安全、最稳定，但对同义表达、复杂描述和跨字段语义覆盖不足。

### 4.2 选择结论

采用路线 2。模型不可用时允许降级为 Dense、BM25、RRF 和确定性规则组合，但任何降级都不得扩大业务写入权限。

## 5. 领域模型

### 5.1 语义关系

```ts
type MatchRelation =
  | 'duplicate'
  | 'highly_similar'
  | 'partial_overlap'
  | 'same_pattern'
  | 'topic_only'
  | 'unrelated'
  | null
```

语义关系描述需求与候选历史数据之间的业务内容关系，不表达系统是否已经确认该关系。

### 5.2 决策状态

```ts
type MatchDecisionStatus =
  | 'confirmed'
  | 'suggested'
  | 'ambiguous'
  | 'rejected'
```

- `confirmed`：只有满足精确、确定性确认条件时使用。
- `suggested`：系统有足够依据给出建议，但仍需用户确认。
- `ambiguous`：依据不足、字段缺失或多个关系无法稳定区分。
- `rejected`：存在确定性冲突或不满足候选资格。

`ambiguous` 不是语义关系；`related` 不作为决策状态。

### 5.3 证据等级

```ts
type MatchEvidenceLevel =
  | 'exact_business_hash'
  | 'exact_normalized_text'
  | 'deterministic_rule'
  | 'model_supported'
  | 'retrieval_only'
```

证据等级只表示结果依据的强弱和来源，不直接决定业务关联状态。

### 5.4 排序字段

```ts
type MatchRanking = {
  finalRank: number
  rankingScore: number
  rankingVersion: string
}
```

- `finalRank` 是当前运行中的最终顺序，从 1 开始且不可重复。
- `rankingScore` 是 `[0, 100]` 范围内的版本化综合匹配分，用于自动排序和界面展示。
- `rankingVersion` 标识评分公式、模型和归一化协议版本。
- `rankingScore` 只允许在相同 `rankingVersion` 内比较，不代表概率，也不能直接触发业务写入。

界面统一显示“综合匹配分”，不得显示为“匹配概率”“成功率”或“准确率”。

## 6. 决策权限

| 处理层 | 允许行为 | 禁止行为 |
| --- | --- | --- |
| 精确业务哈希 | 在候选资格和冲突检查通过后确认重复 | 确认其他语义关系 |
| 确定性硬规则 | 拒绝候选、降低关系等级、标记冲突 | 将建议升级为确认 |
| Dense/BM25/RRF | 召回并融合候选 | 作出业务结论 |
| CrossEncoder | 对候选进行语义重排 | 建立资产关联或修改需求状态 |
| LLM 解释器 | 给出关系建议、证据引用和可读解释 | 升级为 `confirmed` 或修改最终排序分 |
| 用户操作 | 建立正式关联、确认或调整需求状态 | 无额外限制 |

### 6.1 确认重复的必要条件

只有同时满足以下条件，结果才能成为 `relation = duplicate`、`decisionStatus = confirmed`：

1. 需求与候选记录使用同一版本的规范化业务文本协议。
2. 双方 `businessHash` 完全一致。
3. 候选通过权限、生命周期、有效性和项目范围检查。
4. 动作、对象、否定关系和关键约束不存在冲突。
5. 规范化协议所要求的必要字段完整。

仅标题或描述的规范化文本相同，不足以产生 `confirmed`；该情况最多生成 `suggested + duplicate`。

## 7. 统一匹配数据流

```text
需求快照
  -> 权限、生命周期和项目范围预过滤
  -> 精确业务哈希候选注入
  -> Dense 与 BM25 双路召回
  -> RRF 融合 Top50
  -> CrossEncoder 重排 Top20
  -> 确定性字段校验和冲突规则
  -> 计算 rankingScore 与 finalRank
  -> 可选 LLM 批量解释 Top10
  -> 决策策略
  -> 不可变运行与候选快照
  -> 项目管理和 Agent 读取同一结果
```

### 7.1 输入快照

匹配输入必须保存需求快照，至少包含：

- 需求 ID、需求集 ID、项目 ID；
- 标题、描述和现有业务字段；
- 规范化业务文本；
- `businessHash` 和规范化协议版本；
- 需求快照哈希；
- 运行时索引版本和配置哈希。

业务哈希只覆盖语义业务内容，不覆盖更新时间、展示顺序等非语义字段。现有 `requirementSourceHash` 可作为迁移基础，但新协议必须使用明确的版本标识。

### 7.2 候选预过滤

候选过滤必须基于数据库真实存在且有明确语义的字段。允许的过滤维度包括：

- 当前用户有权查看的记录；
- 已删除、已失效或不可用记录；
- 用户选择的资产类型、来源、时间范围；
- 可配置的当前项目排除策略。

不得假设数据库中存在尚未实现的权限或生命周期字段。当前项目数据是否排除必须由匹配请求配置，不能全局硬编码。

### 7.3 召回与融合

- Dense 召回完整清洗后的业务文本。
- BM25/FTS5 召回关键术语、编号、对象和约束。
- 两路结果使用 RRF 融合，默认保留 Top50。
- 精确业务哈希候选必须注入候选集合，并在资格检查通过时保证进入 Top50。
- 各阶段保存原始分数和名次，用于诊断和复现，但原始分数不直接面向用户。

### 7.4 CrossEncoder 重排

- 对 RRF Top50 中排名靠前的 Top20 执行本地 CrossEncoder 重排。
- 模型必须固定 revision、文件哈希和许可信息。
- 模型加载失败时返回明确降级状态，使用融合排序继续处理。
- 不同模型版本的原始分数不可直接比较。

### 7.5 确定性字段与硬规则

硬规则所依赖的动作、对象、约束、否定关系和标识符必须来自：

1. 已审核、结构化的业务字段；或
2. 有版本、可重复执行的确定性解析器。

LLM 临时生成的字段不能作为确认或硬拒绝的唯一依据。必要字段缺失时，结果不得成为 `confirmed`。

硬规则只允许：

- 确认精确业务哈希重复；
- 将候选降级为更弱关系；
- 标记为 `ambiguous`；
- 因确定性冲突标记为 `rejected`。

### 7.6 综合匹配分与最终排序

`rankingScore` 必须由版本化、确定性的评分器计算。输入可以包含：

- 精确业务哈希证据；
- RRF 融合名次；
- CrossEncoder 同版本归一化分数；
- 确定性字段一致性加分；
- 动作、对象、否定关系和约束冲突扣分。

LLM 输出不得参与 `rankingScore`，避免模型解释波动改变排序。

每个 `rankingVersion` 必须对应一份可校验哈希的评分清单。清单明确记录组件分数变换、权重、加分、扣分、分数上限、分数下限和稳定排序规则，生产代码中不得散落未登记的评分常量。初始版本遵守以下不变量：

- 通过全部资格检查的精确业务哈希重复记录固定为 100 分；
- `rejected` 固定为 0 分且不进入默认候选列表；
- 仅规范化文本相同但不满足业务哈希确认条件时，最高为 99 分且保持 `suggested`；
- 存在动作、对象、否定关系或关键约束硬冲突时固定为 0 分；
- 其他输入不变时，更高的同版本 CrossEncoder 分数不得得到更低的 `rankingScore`；
- CrossEncoder 降级运行使用独立的 `rankingVersion`，不得沿用包含重排器的评分版本。

除上述固定边界外，组件权重由评分清单管理，并通过自动化回归、排序稳定性和性能门验证；它们不被解释为人工校准参数。

最终排序规则按以下优先级执行：

1. 通过资格检查的 `confirmed + duplicate`；
2. 其他未拒绝候选按 `rankingScore` 降序；
3. 同分时依次按 CrossEncoder 名次、RRF 名次、记录 UID 稳定排序；
4. `rejected` 候选默认不展示，可在诊断模式下置于末尾查看。

评分公式、归一化参数或模型变化时必须升级 `rankingVersion`。跨版本界面不得直接比较分数变化，只能比较各自运行内的名次和关系。

### 7.7 可选 LLM 解释

- 只对最终 Top10 批量生成解释。
- 输入必须按不可信外部数据处理，使用严格结构化协议。
- 输出必须校验 UID、关系枚举、证据引用和字段长度。
- LLM 只能补充解释和提出关系建议，不能修改 `rankingScore`、`finalRank` 或将结果升级为 `confirmed`。
- 在线模型必须有显式开关、字段脱敏和外部数据授权；默认使用本地模型或关闭解释。
- 解释失败时保留确定性排序和决策，不得产生业务写入。

## 8. 存储设计

### 8.1 匹配运行

新增不可变运行实体：

```ts
type RequirementMatchRun = {
  id: string
  requirementId: string
  requirementSnapshotHash: string
  requirementBusinessHash: string
  normalizationVersion: string
  indexVersion: string
  pipelineVersion: string
  rankingVersion: string
  modelVersion: string | null
  configHash: string
  status: 'running' | 'succeeded' | 'failed' | 'stale'
  degradationCodes: string[]
  failureCode: string | null
  startedAt: string
  completedAt: string | null
}
```

重新匹配必须创建新运行，不覆盖旧运行。默认读取最近一次成功、未失效且与当前需求快照兼容的运行。

### 8.2 候选结果

```ts
type RequirementMatchCandidate = {
  runId: string
  recordUid: string
  recordSnapshotHash: string
  denseRank: number | null
  denseScore: number | null
  lexicalRank: number | null
  lexicalScore: number | null
  fusedRank: number
  rerankerRank: number | null
  rerankerScore: number | null
  finalRank: number
  rankingScore: number
  relation: MatchRelation
  decisionStatus: MatchDecisionStatus
  evidenceLevel: MatchEvidenceLevel
  reasonCodes: string[]
  evidenceJson: unknown
  explanation: string | null
}
```

数据库存储原始阶段分数用于诊断；对外 API 默认只返回最终排名、综合匹配分、关系、决策状态、证据和必要的候选摘要。

### 8.3 正式关联来源

资产关联表增加来源和确认信息：

```ts
type LinkSource =
  | 'manual'
  | 'exact_business_hash'
  | 'legacy_unknown'
```

正式关联至少保存 `linkSource`、`confirmedBy`、`confirmedAt` 和可选的 `matchRunId`。人工确认时 `confirmedBy` 保存用户标识；精确业务哈希确认时保存固定系统主体 `system:exact-business-hash`。语义建议不能直接写入正式关联表。

## 9. API 与界面契约

### 9.1 匹配请求

匹配请求至少包含：

- `requirementId`；
- 候选范围过滤条件；
- 当前项目记录包含或排除策略；
- 是否启用解释；
- 预期管线版本，可为空表示使用当前正式版本。

启动接口返回运行 ID。调用方通过运行状态接口查询进度，通过结果接口分页读取候选。

### 9.2 匹配结果

结果默认按 `finalRank` 升序返回，并展示：

- 排名；
- 历史数据名称和来源；
- 综合匹配分；
- 语义关系；
- 决策状态；
- 证据标签和理由；
- 是否已经正式关联；
- 用户确认或查看详情操作。

界面必须明确说明：“综合匹配分表示当前算法版本内的相对匹配程度，不代表统计概率。”

自动匹配完成后，系统只更新候选建议列表。用户确认后才能建立正式资产关联；需求是否满足仍由既有业务审核流程决定。

## 10. 错误处理与封闭失败

以下情况必须使运行失败或明确降级，并保证业务写入数量为零：

- 索引版本与运行声明不一致；
- 需求快照在运行期间发生不兼容变化；
- 规范化协议或评分版本无法加载；
- 模型输出包含未知 UID、非法枚举或无效证据引用；
- 数据库运行或候选结果写入不完整；
- 用户无权访问需求或候选记录。

允许降级的情况：

- CrossEncoder 不可用时降级到 RRF 排序；
- LLM 解释不可用时保留确定性排序并省略解释；
- 单个候选文本异常时记录候选错误并继续处理其他候选。

所有降级必须记录 `degradationCodes`，并在界面中提示本次运行采用了降级能力。

## 11. 历史数据迁移

1. 现有资产关联统一回填为 `legacy_unknown`，除非已有可靠字段可以证明为人工关联。
2. 现有 AI 自动设置的满足状态标记为 `legacy_unverified`。
3. 不自动解除历史关联，不自动重置历史需求状态。
4. 遗留关联不能作为弱监督正样本或自动化质量门的正确答案。
5. 旧匹配结果只供历史查看，不进入新版本质量指标。
6. 新旧结果必须能通过 `pipelineVersion` 和 `rankingVersion` 明确区分。
7. 第一阶段必须先关闭现有分数触发的自动关联和自动满足逻辑，再启用新管线。

需求状态来源协议增加 `manual`、`system_rule` 和 `legacy_unverified`。迁移只回填来源字段，不改变现有状态值；`legacy_unverified` 状态必须在界面显示待复核提示，且不得作为新匹配管线的输入事实。

## 12. 排除人工评测后的自动化质量门

自动化评测只证明已知事实一致性、安全性、确定性和技术稳定性，不证明真实业务语义准确率。

### 12.1 强制发布门

1. 符合候选资格的精确业务哈希重复记录 `Recall@50 = 100%`。
2. 改变动作、对象、否定关系或关键约束后，不得产生 `confirmed`。
3. 模型协议错误、证据错误、UID 越界时，正式资产关联和需求状态写入数量必须为零。
4. 索引版本不一致时，不得生成成功运行。
5. 同一数据、索引、配置和模型版本重复执行，`finalRank`、`rankingScore`、关系和决策状态必须稳定。
6. `suggested`、`ambiguous` 和 `rejected` 不得自动建立正式关联或修改需求状态。
7. 评分公式变化而 `rankingVersion` 未升级时，契约测试必须失败。
8. 项目管理与需求分析 Agent 对同一输入、范围和版本必须返回相同候选顺序与决策。

### 12.2 变形测试

固定样本生成以下确定性变体：

- 仅调整空白、HTML 包装、字段顺序和等价标点，结果应保持稳定；
- 替换为同一规范化标识符，精确匹配能力应保持；
- 修改动作、对象、否定关系或关键约束，不得确认重复；
- 加入无关长文本，不得使无关候选升级为确认；
- 删除必要业务字段，确认结果必须降级。

### 12.3 趋势指标

以下指标只用于版本间趋势观察：

- 合成同义改写 Recall@K；
- 对抗字段变换拒绝率；
- 弱监督结构事实一致率；
- 多模型关系一致率；
- 候选集合和排序漂移；
- P50/P95 延迟、峰值内存和模型体积。

多模型共识、合成数据和弱监督结果不得作为自动建立业务关联的依据。

### 12.4 性能门

使用固定硬件档案、固定数据快照和固定模型资源运行基线：

- P95 端到端延迟相对正式基线回退不得超过 20%；
- 峰值内存相对正式基线回退不得超过 25%；
- 基线报告必须记录是否包含模型加载、CrossEncoder 和解释阶段；
- 不包含真实重排器或解释器的合成基准不得替代端到端性能结论。

## 13. 分阶段实施

本重构拆分为四个按顺序实施的子项目，每个子项目单独形成实施计划、验证结果和验收记录。

### 阶段 1：安全止血与历史迁移

- 移除或禁用现有分数触发的自动关联和自动满足。
- 增加遗留关联和遗留状态来源标识。
- 建立“建议结果零业务写入”安全回归。
- 保持现有匹配读取界面可用。

### 阶段 2：统一匹配核心与决策策略

- 抽离项目管理和 Agent 共用的匹配核心。
- 实现规范化业务文本、业务哈希、候选预过滤和召回融合。
- 实现 CrossEncoder 重排、确定性规则、`rankingScore` 和决策矩阵。
- 保证 LLM 不参与最终排序分和确认决策。

### 阶段 3：运行级存储、IPC 与界面

- 引入不可变运行和候选快照。
- 调整 IPC、共享类型和分页查询契约。
- 匹配明细界面展示排名、综合匹配分、关系、状态、证据和降级提示。
- 保留用户确认关联入口，并继续遵守现有主题、弹窗、表格滚动和列宽规范。

### 阶段 4：自动化质量门与切换

- 建立确定性、变形、协议故障、跨入口一致性和性能回归。
- 新管线先执行影子运行，不影响现有读取结果。
- 门禁通过后切换项目管理和 Agent 读取入口。
- 旧管线只读保留一个兼容周期，再按独立变更移除。

依赖顺序固定为：`阶段 1 -> 阶段 2 -> 阶段 3 -> 阶段 4`。

## 14. 验收标准

### 14.1 功能验收

- 用户可以根据项目需求内容启动历史数据自动匹配。
- 系统返回按综合匹配分排序的 Top N 候选。
- 精确重复、语义建议、模糊结果和拒绝结果有明确区分。
- 用户可以查看匹配证据、历史数据详情和本次运行版本。
- 只有用户确认或精确业务哈希确认流程才能建立正式关联。
- 匹配结果不会自动将需求设置为“已满足”。

### 14.2 契约验收

- 项目管理与 Agent 共用相同匹配核心和候选 DTO。
- 运行、候选、关联来源和版本字段均可追溯。
- 相同版本内排序稳定；不同版本不会被错误比较。
- 模型解释失败不影响确定性排序，也不产生业务写入。

### 14.3 测试验收

- 所有强制发布门均有自动化测试并通过。
- TypeScript 检查、项目管理 smoke、需求匹配契约回归和 Agent 匹配 smoke 通过。
- 迁移测试覆盖旧关联、旧 AI 状态、重复执行和回滚读取。
- 性能报告明确区分纯检索、真实重排和解释阶段。

## 15. 风险与约束

1. 排除人工评测后，不能证明开放业务语义的真实准确率；语义结果必须保持建议属性。
2. `rankingScore` 是版本内相对排序分，若界面文案不清晰，仍可能被误解为概率。
3. 当前历史关联缺少可靠来源，迁移后只能标记为 `legacy_unknown`，不能用于训练或评测。
4. 规范化业务文本协议直接影响精确重复确认能力，协议升级必须与哈希版本同步。
5. 本地 CrossEncoder 的资源和延迟必须在目标硬件上验证，不能仅依赖不加载模型的合成基准。

## 16. 实施准入

本设计批准后仍不能直接进入生产代码修改。下一步必须先基于本规格使用 `superpowers:writing-plans` 生成详细实施计划，并将四个阶段拆成可独立验证、可回滚的任务。实施过程需遵循测试驱动、隔离工作区、代码审查和完成前验证流程。
