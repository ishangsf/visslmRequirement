# 项目需求与资产历史数据匹配 v1.5 构建与准确性验证设计

> 状态：已批准，待实施计划
>
> 批准日期：2026-08-28
>
> 目标版本：1.5.0

## 1. 背景

项目需求与资产历史数据匹配 v1.1 已完成统一匹配核心、不可变运行、候选排序、安全决策和项目管理界面接入。当前需要基于最新代码构建正式 Windows 安装包，生成贴合项目需求匹配业务的自动化测试数据，并在不建设人工评测集的前提下验证匹配结果的技术准确性、安全性和稳定性。

本工作区作为 Delivery Orchestrator，负责方案、任务拆分、集成、验证、验收与最终结论。具体实施由受控子 agent 完成，子 agent 不作最终接受决定，也不得继续委派。

## 2. 目标

1. 将应用版本从 `1.4.15` 升级到 `1.5.0`，同步应用元数据、锁文件和安装包名称。
2. 从最终代码提交构建完整 Windows 安装包，并记录文件路径、大小和 SHA-256。
3. 生成可重复、可审计、与真实业务关系对应的项目需求和资产历史数据。
4. 使用生产匹配核心、真实本地 Embedding、BM25/FTS5、RRF 和 `Xenova/bge-reranker-base` 执行评测。
5. 输出自动化硬门、排序指标、逐场景结果和限制说明。
6. 对打包应用执行资源完整性、启动和项目匹配流程 smoke，证明评测对象与发布物一致。

## 3. 非目标

- 不建立人工标注评测集。
- 不把合成场景指标表述为开放域真实业务准确率。
- 不使用历史未知来源关联作为正确答案。
- 不让 LLM 解释结果参与排序或评测标签。
- 不在当前高配开发机上替代后续目标机性能门禁。
- 不将测试数据写入用户真实数据库。
- 不发布 GitHub Release，也不推送远端，除非用户另行明确要求。

## 4. 采用方案

采用“业务事实构造数据 + 真实本地模型 + 自动排序指标 + 打包应用 smoke”方案。

没有采用以下方案：

- 历史关联弱标签：来源不可靠，无法形成可信正确答案。
- 仅复用现有少量固定样本：覆盖面不足，无法计算有意义的排序指标。
- 模拟 reranker：不能证明真实本地 CrossEncoder 的排序行为。

## 5. 版本与发布物

- 目标版本：`1.5.0`。
- 安装包目标名称：`VISSLM-Agent-Setup-1.5.0.exe`。
- 使用 `npm run package` 构建完整 Windows 安装包。
- 构建前必须通过模型资源和运行时依赖校验。
- 构建报告记录 Git 提交、版本、构建时间、安装包大小和 SHA-256。
- 若评测发现生产代码缺陷并产生修复，必须从修复后的最终提交重新构建，旧安装包作废。

## 6. 测试数据设计

### 6.1 数据规模

- 24 条项目需求作为查询基准。
- 约 600 条资产历史记录作为候选集合。
- 固定随机种子、稳定 UID 和版本化数据清单。
- 数据集与预期标签写入 `test-data/requirement-matching/v1.5/`。

### 6.2 业务域

测试需求至少覆盖：

- 需求管理；
- 配置管理；
- 缺陷管理；
- 数据采集与同步；
- 权限与审批；
- 查询、报表与状态展示。

### 6.3 关系与对抗场景

每个业务域组合下列场景：

- 精确业务重复；
- 仅空白、标点、HTML 包装或字段顺序变化；
- 高度相似；
- 部分重叠；
- 同模式但对象不同；
- 仅主题相关；
- 完全无关；
- 动作冲突；
- 对象冲突；
- 否定关系冲突；
- 标识符冲突；
- 关键约束冲突；
- 必要字段缺失；
- 同标题但描述不同；
- 长无关噪声文本；
- 当前项目排除与候选资格过滤。

### 6.4 标签来源

标签由生成规则直接确定，并保存生成器版本、种子、场景类型、相关性等级和理由码。标签不来自人工主观判断，也不从历史关联反推。

用于 NDCG 的等级定义为：

- 4：符合资格的精确业务重复；
- 3：高度相似；
- 2：部分重叠；
- 1：同模式或主题相关；
- 0：无关或确定性冲突。

## 7. 评测执行链路

```text
版本化场景清单
  -> 隔离临时数据库
  -> 生成项目需求和资产历史记录
  -> 真实本地 Embedding 建索引
  -> Dense + BM25/FTS5 双路召回
  -> RRF Top50
  -> 真实 CrossEncoder Top20
  -> 确定性规则与 rankingScore
  -> 不可变运行和候选结果
  -> 指标计算与逐场景报告
  -> 打包应用资源/启动/匹配 smoke
```

- 评测必须使用生产匹配核心，不复制一套独立排序算法。
- LLM 解释关闭，因为它不参与最终排序，且会引入网络和非确定性。
- 真实 CrossEncoder 不可用、模型身份不符或出现降级时，本次准确性评测无效并退出非零。
- 所有数据和用户目录使用临时隔离路径，结束后不污染真实应用数据。

## 8. 指标与门禁

### 8.1 强制硬门

- 符合资格的精确业务重复 `Recall@50 = 100%`。
- `confirmed` 结果精确率 `100%`。
- 动作、对象、否定、标识符和关键约束冲突的误确认率为 `0`。
- `suggested`、`ambiguous` 和 `rejected` 产生的正式业务写入数为 `0`。
- CrossEncoder 降级次数为 `0`。
- 相同数据、模型、索引和配置重复执行的排序一致率为 `100%`。
- 项目管理入口和需求分析 Agent 的候选顺序与决策投影一致。

### 8.2 构造场景工程指标

- 构造语义正例 `Recall@5 >= 90%`。
- `MRR >= 0.80`。
- `NDCG@10 >= 0.85`。
- 同时报告 `Recall@1`、`Recall@10`、`Recall@50` 和逐关系召回。

这些指标只用于本数据生成协议下的工程验收和版本趋势，不代表开放域真实业务准确率。

## 9. 打包应用验证

安装包构建完成后至少验证：

- 安装包版本为 `1.5.0`；
- 打包资源包含固定 revision 和 SHA-256 的 Embedding 与 CrossEncoder；
- 应用可从隔离用户目录启动；
- 项目管理匹配流程可启动并返回按 `finalRank` 排序的结果；
- 运行元数据、模型身份和降级状态可读取；
- 正式业务关联和需求状态没有被语义建议自动修改。

权威排序指标由生产核心在隔离数据库上计算；打包应用 smoke 用于证明发布物包含相同模型资源和可用链路，不单独复制指标算法。

## 10. 子 agent 分工

所有子 agent 使用 `gpt-5.6-luna`、`max` 推理，不得生成后代 agent。

### 10.1 `prd`

- 编写可追踪的业务场景矩阵、标签规则和验收映射。
- 只修改指定需求/场景文档。
- 不实现代码或测试。

### 10.2 `backend`

- 升级版本号和锁文件。
- 实现数据生成/评测入口及必要的生产缺陷修复。
- 只修改指定脚本、后端文件和包元数据。
- 所有行为变更遵循 TDD。

### 10.3 `testing`

- 生成版本化测试数据、回归测试和验证报告。
- 构建完整安装包并核对发布物。
- 首轮与集成后复测均记录精确命令、退出码和指标。
- 不修改生产代码来使测试通过。

### 10.4 独立 `testing` 复审

- 只读审查实现、数据和报告。
- 独立复跑关键门禁与指标。
- 报告缺陷、证据、风险和阻塞，不扩大修改范围。

## 11. 执行顺序与依赖

1. `prd` 固定场景矩阵和数据契约。
2. `backend` 与首轮 `testing` 在契约稳定后并行工作，写入范围保持互斥。
3. 根 agent 检查并集成子 agent 结果，解决契约差异。
4. `testing` 从最终提交构建 `1.5.0` 安装包并执行完整评测。
5. 独立 `testing` 复审并复跑关键结果。
6. 若发现生产缺陷，由 `backend` 按 TDD 修复，随后返回步骤 4。
7. 根 agent 根据所有证据给出 `ACCEPTED`、`ACCEPTED_WITH_RISKS` 或 `REJECTED/BLOCKED`。

## 12. 错误处理

- 模型资源缺失、哈希错误或 CrossEncoder 降级：评测失败，不输出准确性通过结论。
- 数据清单或预期标签 schema 不合法：生成和评测均失败。
- 指标未达门槛：输出逐场景失败明细，区分实现缺陷、生成数据歧义和模型能力限制。
- 生产代码缺陷：新增失败回归后修复，重新构建和完整复测。
- 构建失败：保留完整日志，不使用旧安装包替代。
- 打包 smoke 失败：不得仅凭源码级指标接受发布物。
- 目标机性能门禁不在本次关闭，必须在报告中继续保留为独立风险。

## 14. 验收条件

只有同时满足以下条件才能接受本次工作：

1. 安装包由最终代码提交构建，版本为 `1.5.0`。
2. 测试数据规模、场景和标签来源符合本设计。
3. 评测使用真实本地模型和生产匹配核心，且无 CrossEncoder 降级。
4. 第 8 节全部硬门和工程指标通过。
5. 打包应用 smoke 通过。
6. TypeScript、需求匹配回归、项目管理 smoke 和生产构建通过。
7. 独立复审没有未解决的 Critical 或 Important 缺陷。
8. 报告明确说明合成数据的结论边界和目标机性能残余风险。
