# VISSLM Agent 需求分析专家精准匹配：AI 深度语义卡片优先目标

> 用途：立项、开发验收和发布评审。
>
> 本版本将查询匹配重构为“全量原文召回 + 结构化语义增强 + Cross-Encoder 精排 + 确定性评分 + 一次批量 AI 解释”。语义卡片是按数据中心记录持久化的 AI 语义资产，不是查询阶段的临时对象。人工标注、人工裁决和 Excel 样本包明确排除。

## 1. 建设目标与不可妥协原则

建设 VISSLM Agent 的“需求分析专家精准匹配能力”。用户通过 `@需求分析专家` 输入一个或多个数据中心需求编号后，系统精确定位基准需求，在可用的数据中心记录中识别业务目标真正相同、相近或部分重叠的需求，并返回名称、描述、模块、需求类型、匹配关系、可解释的综合匹配度和原文证据。

精准匹配以业务目标为准，不以关键词、产品域、模块、记录类型或向量分数相同为充分条件。系统需要比较需求类型、功能对象、目标动作、当前状态、目标状态、触发条件、输入、输出、功能行为、业务约束、业务场景和验收结果；仅主题相同、模块相同或动作模式相同但业务对象不同的记录，不得直接判为正式匹配。

以下原则是本目标的硬约束：

1. **完整清洗原文和明确原始字段是唯一事实来源**。任何 AI 卡片、召回分、重排分或历史分析结果都不是事实来源。
2. **语义卡片必须先成为持久化数据资产**。查询阶段禁止为基准、候选或前 20 条记录临时生成卡片。
3. **语义资产与查询职责分离**。资产中心采用已落地的 `standard`/`strict` 质量路由，而不是所有记录固定三阶段：`standard` 健康路径执行一次结构化抽取，只有失败或核心字段低置信时才做一次定向修复；`strict` 执行 `initial` 与独立 `independent` 复核，只有分歧或低置信时才执行 `adjudication`。查询阶段不得生成卡片，只消费当前签名下的 `ready` 卡片增强召回和评分。不得用正则、关键词、低成本启发式或半成品卡片代替资产分析。
4. **原文召回覆盖全量当前索引，`ready` 卡片只做语义增强**。基准与候选记录只要原文可读、且候选存在于当前 embedding 索引，即可进入 Dense/BM25/Cross-Encoder/AI 复核。无有效 AI 卡片的基准或候选使用 `source_only` 原文视图，不得被静默排除。
5. **失败关闭与可验证输出**。上述每个路由的每次模型输出仍必须通过严格 JSON Schema、`recordUid`、逐字段证据、逐字段置信度、枚举和核心字段校验；任一校验或持久化失败时，记录进入 `failed`，不退回正则语义卡片，不使用旧卡片冒充当前有效卡片。`requirementType`、`productDomain`、`module` 等已知字段由服务端从明确原始字段注入，模型不得重复生成或覆盖。
6. **人工标注/Excel 样本包不在范围内**。本目标不新增人工金标、双人标注、人工裁决、Excel 标注数据或依赖人工标签的质量指标。

单次模型请求设置 15 分钟安全上限；性能优化通过缩短 standard/strict 的输出预算和将结构校验重试限制为一次定向修复实现，不放宽证据、Schema、UID、置信度、枚举或失败关闭约束。trace 在阶段开始/完成、模型错误、分歧和终态等阶段边界持久化，完整指标平台不属于本轮交付。

## 2. 原文清洗与事实边界

### 2.1 唯一事实来源

每条数据中心记录必须保存可重建的完整清洗原文 `cleanedSource`，并保留来源 `recordUid`、名称、描述和明确的原始字段值。完整清洗原文由原始记录字段确定性生成，至少包括：

- HTML 实体解码；
- HTML 标签、脚本、样式和控制字符清除；
- 空白、换行和明显格式噪声的确定性归一化；
- 已明确列入清洗规则的发布版本、处理意见、历史回复等非需求元数据清除；
- 保留所有业务含义文本、原有顺序和字段边界；不得为了性能截断用于哈希、召回或 AI 分析的原文。展示摘要可以截断，但不能替换资产中的完整清洗原文。

明确字段只能通过已登记的字段别名从原始数据读取，例如需求类型、模块、产品域等。字段别名读取只返回原始字段的清洗值；字段缺失就保持空，不根据描述中的词语猜测字段值。若使用 `normalizedText`，它只能是由原始字段确定性清洗得到的派生快照，不能成为独立事实来源，且必须纳入内容哈希。

### 2.2 正则与规则的允许边界

正则和字符串规则只允许用于：

- HTML/实体/控制字符清洗；
- 已明确登记的字段别名读取或字段路径定位；
- 不改变语义的空白与格式归一化。

正则绝不允许推断或生成 `action`、`functionalObject`、当前状态、目标状态、触发条件、输入、输出、功能行为、业务约束、验收结果、业务场景或产品域等业务语义。禁止根据“新增/修改/异常/支持/按钮/页面”等关键词推断动作、对象或状态；禁止把需求类型 `Defect` 自动推断为 `fix_defect`；禁止把模块相同推断为业务目标相同。standard 的定向修复和 strict 的独立复核/裁决仍必须回到 AI 结构化输出并通过同一套验证，不能用规则补齐。

清洗快照可以用于定位原文和构造召回输入，但它不是语义卡片。没有完成所选质量路由及其最终验证的记录不得因为拥有清洗快照而被视为已语义化。

## 3. 语义卡片资产契约

### 3.1 持久化状态

每条数据中心记录都必须有语义化资产状态。存储枚举和用户界面中文标签固定如下：

| 存储状态 | 用户界面标签 | 含义 | 是否可进入匹配 |
| --- | --- | --- | --- |
| `pending` | 待处理 | 没有当前签名下的有效卡片，等待人工触发生成或重新生成 | 否 |
| `processing` | 处理中 | 正在执行该记录的 AI 卡片分析，结果尚未提交 | 否 |
| `ready` | 已就绪 | 所选质量路由完成，最终卡片和全部元数据通过校验，且仍与当前原文和签名一致 | 是 |
| `failed` | 失败 | 分析、模型、持久化或校验失败，没有可消费的有效卡片 | 否 |

允许的主要状态转移为：

```text
新记录/内容变化/版本变化 -> 待处理
待处理 --资产中心执行--> 处理中
处理中 --standard/strict 路由成功且校验通过--> 已就绪
 处理中 --任一阶段或校验失败--> 失败
失败 --资产中心重试--> 处理中
已就绪 --内容哈希、分析器版本或模型签名变化--> 待处理
```

`processing` 不能被结构化语义召回读取。应用重启、任务中断或锁失效后，未提交完整结果的任务必须回到 `failed` 或按产品定义重新进入 `pending`，不得伪装成 `ready`。

### 3.2 内容哈希、版本签名与自动失效

语义资产必须至少持久化以下元数据：

- `recordUid`：数据中心记录唯一 UID；
- `contentHash`：完整清洗原文和明确原始字段的规范化内容哈希；
- `analyzerVersion`：清洗规则、字段别名、卡片 schema、提示词和解析/校验逻辑的版本；
- `modelSignature`：模型提供方、模型 ID、revision/版本、关键推理配置和语义卡片提示词签名；
- 最终卡片 JSON、所选路由的阶段结果摘要、状态、错误信息、创建时间和更新时间。

逻辑缓存身份必须同时包含 `recordUid`、`contentHash`、`analyzerVersion` 和 `modelSignature`。以下任一变化都必须自动使原 `ready` 资产失效为 `pending`，不再作为结构化语义增强资产参与匹配，并等待资产中心重新生成；原始数据仍保留在当前文本/向量召回范围内：

- 原始字段或完整清洗原文变化；
- 内容哈希变化；
- 清洗规则、字段别名、schema、提示词、解析器或校验器变化；
- 模型提供方、模型、revision、关键推理配置或模型签名变化。

缓存命中必须同时满足：状态为 `ready`、四项身份元数据完全匹配、卡片 JSON 可解析、schema 校验通过、所有证据仍能在当前清洗原文中找到、所有置信度和枚举合法。任一条件不满足即为缓存未命中并转为 `pending`，绝不能复用旧卡片或只比较 UID。

卡片只在所选路由的最终结果完整通过校验后原子写入并切换为 `ready`。standard 无需无条件执行 `independent`/`adjudication`；strict 也只在存在分歧或低置信时进入 `adjudication`。处理中或失败的部分结果不可被查询、召回、重排或展示为当前卡片。

### 3.3 卡片字段与证据契约

最终语义卡片至少包含以下字段：

- `requirementType`、`productDomain`、`module`；
- `functionalObject`、`action`；
- `currentState`、`targetState`、`trigger`；
- `input`、`output`、`behavior`；
- `constraints`、`acceptance`、`businessScene`；
- `recordUid`、`contentHash`、`analyzerVersion`、`modelSignature`、`analysisStatus`、`analysisSummary`。

每一个语义字段都必须同时返回：

```json
{
  "value": "字段值；无法从原文确认时为空",
  "evidence": "从完整清洗原文逐字复制的短句",
  "confidence": 0.0
}
```

证据必须是对应记录完整清洗原文中的可验证原文片段；明确原始字段的证据必须来自该字段的清洗值。不得将模型改写、概括、补全或常识推断冒充原文证据。字段无法确认时，`value` 为空、`evidence` 为空、`confidence` 为 `0`，而不是猜测一个值。`confidence` 取值范围为 `0..1`，表示该字段在当前原文证据下的模型置信程度，不解释为统计概率或准确率。

`action` 只能是以下枚举之一：

```text
rename_label | configure_permission | compare | enable_selection |
add_capability | remove_capability | relax_constraint |
tighten_constraint | fix_defect | change_flow | optimize_ui | unknown
```

`unknown` 是合法的保守结果，不得用默认动作代替缺失证据。卡片的 `matchingText` 可以由最终卡片和完整清洗原文确定性拼接，但不得删掉原文或把模型推断写回原文。

本轮语义化服务仍由模型返回并校验逐字 `evidence` 文本；将原文预切分为 `evidenceIds` 再由服务端解引用的证据 ID 化方案尚未实现，属于后续性能阶段，不得作为当前交付或验收前提。匹配解释中的证据编号若另有契约，也不能替代语义卡片的原文证据校验。

## 4. 资产中心的 AI 语义化流程

### 4.1 资产中心操作

资产中心必须提供语义化状态列和按状态筛选，至少支持筛选“待处理、处理中、已就绪、失败”。每条记录支持单条“生成/重新生成 AI 语义卡片”，并支持对勾选记录、当前页待处理记录以及数据中心全部未语义化记录执行批量生成。“全部未语义化”必须由后台按当前 `contentHash + analyzerVersion + modelSignature` 实时计算，覆盖缺失、失败、内容变化、分析器变化和模型变化的记录，排除当前签名下仍然有效的 `ready` 资产。

点击“处理全部未语义化数据”时，后台按当前 `contentHash + analyzerVersion + modelSignature` 收集全部未就绪记录，不设置产品层面的单任务数量上限；任务会自动持续处理，直到本次收集的记录全部完成或用户暂停/终止。单条记录内部按所选质量路由执行：standard 健康路径为一次结构化抽取，失败或核心字段低置信时才做定向修复；strict 为 `initial + independent`，仅分歧或低置信时才做 `adjudication`。本轮实现仍按候选列表逐条处理记录，跨记录有界并发属于后续优化，不得把它写成已交付能力；记录内 strict 的两次独立调用可以并行。

批量任务必须提供详细任务快照，至少展示任务状态、当前记录名称/编号/序号、当前 AI 阶段、总量、可处理总数、成功数、失败数、剩余数、最近处理结果、单条耗时和失败原因。当前快照和候选队列由服务进程内存维护，页面在同一进程存活期间可重新读取；持久化 job manifest、租约、进程重启后的恢复本轮尚未实现，后续阶段不得将其描述为已交付。应用重启或任务中断不得把半成品标记为 `ready`。

资产中心必须提供“可审计 AI 分析过程”，但不得把模型隐藏思维链或逐 Token 推理伪装成可审计信息。实时过程至少包含阶段开始/完成、模型响应校验、失败原因和重试次数；每个实际执行的分析阶段完成后展示模型主动返回且已通过校验的结构化字段值、置信度和原文逐字证据。strict 的独立复核完成后展示其与初步分析的字段分歧，触发裁决后展示每项分歧的最终采用值和证据；standard 不应伪造未执行的独立复核或裁决阶段。界面必须明确标注“不是模型内部思维链”，不得展示或持久化未经校验的模型原始响应。

每条记录的审计轨迹必须与最终语义卡片一并写入 `analysis_trace_json`，失败记录也要保留截至失败点的阶段、重试和校验事件。当前实现保留内存/IPC 中的完整事件流，并在阶段开始/完成、模型错误、分歧及终态等阶段边界持久化；任务结束后可从资产中心记录详情回看同一份轨迹。审计轨迹只能包含结构化业务结论、证据和系统事件，不包含 API 密钥、完整请求体、原始模型响应或隐藏推理内容。完整指标聚合/监控平台不属于本轮交付。

任务必须支持暂停、继续和终止。暂停或终止在当前 AI 调用的安全阶段边界生效：请求发出后不强杀模型调用，不把半成品写成 `ready`；暂停后不再进入下一阶段或下一记录，继续后从安全边界恢复；终止后不再开始后续记录，已经完成的卡片保留，当前未完成和尚未开始的记录恢复/保持为待处理。系统同一时间只允许一个活动语义化任务，活动任务期间禁止创建相互冲突的新任务。

资产中心是语义卡片的唯一常规生成入口。数据同步、导入或原始字段变化可以自动登记 `pending`，但不得在用户查询时偷偷触发 AI 生成。语义卡片是结构化召回和解释增强资产，不是匹配开关：基准或候选卡片处于 `pending`、`processing`、`failed` 或版本失效时，只要数据中心仍有可读名称、描述或规范化原文，查询必须使用完整清洗原文继续 Dense/BM25、Cross-Encoder、确定性评分和一次批量 AI 解释，不得要求用户先到资产中心处理后才能匹配。只有原始文本也为空时，才允许以缺少可分析内容结束该条查询。

### 4.2 标准/严格自适应深度分析

任务开始时锁定质量模式。`qualityMode=standard` 为默认的低成本健康路径，`qualityMode=strict` 用于需要独立复核的高风险或抽查场景；历史调用方传入 `deepThinking=true` 时等价于 strict，未传或为 false 时等价于 standard。同一任务内不得切换模式。两种模式都必须回到完整清洗原文和明确字段，且每次 AI 输出都必须通过同一套结构化校验。

1. **standard**：执行一次 `initial` 结构化抽取。服务端直接注入 `requirementType`、`productDomain`、`module` 等已知字段，模型只分析其余语义字段。若初步结果通过结构、UID、证据、置信度、枚举和核心字段校验且核心字段置信度达到门槛，直接进入持久化；若核心字段失败或低置信，只对这些字段执行一次定向修复，不启动 `independent` 或无条件 `adjudication`。修复结果仍须完整验证，失败即整条记录 `failed`。
2. **strict**：对同一份 source-only 原文并行执行不互相读取结论的 `initial` 与 `independent`。两份结果都通过验证后，程序比较字段分歧和核心字段置信度；仅在存在分歧或低置信时调用 `adjudication`，并只提交需要裁决的字段，稳定字段由服务端合并。无分歧且核心字段足够可信时，直接选择较高置信的已验证字段，不发起第三次模型调用。裁决结果仍须完整验证，失败即整条记录 `failed`。

`initial`、`independent`（strict 下）和 `adjudication`（触发时）都使用结构化 schema；独立复核不得接收 `initial` 输出，裁决不得以正则或未经验证的程序猜测替代 AI 结论。standard/strict 的单次模型请求均有 15 分钟安全上限；输出预算按模式和阶段收紧，结构校验最多一次定向修复，不做相同请求的级联重放。任一调用超时、模型不可用、输出无法解析、schema 不合法、UID 不匹配、证据不受原文支持、置信度越界或枚举非法，整条记录进入 `failed`，不生成可用卡片。

### 4.3 失败关闭与禁止回退

以下情况均必须失败关闭：

- JSON/schema 缺字段、未知字段、额外字段、类型错误或结构不完整；
- `recordUid`、`contentHash`、`analyzerVersion` 或 `modelSignature` 与任务输入不一致；
- 任一语义字段缺少证据或证据不是对应完整清洗原文的原文片段；
- 任一置信度不是有限数值或不在 `0..1`；
- `action` 或其他枚举字段出现未知值；
- 所选质量路由无法形成通过校验的最终字段结果；
- 持久化写入不完整、卡片校验失败或资产状态更新失败。

失败时保留可诊断的错误原因和阶段信息，但不输出 `ready` 卡片，不把 `source_only` 清洗快照当成语义卡片，不调用 `buildRequirementSemanticCard` 或等价正则逻辑作为回退，不使用上一次内容/版本/模型签名的旧卡片。自动重试也必须重新经过当前签名下的 AI 阶段；standard 使用标准预算，strict 使用严格预算，最多一次定向修复，不因重试改变任务质量模式。

## 5. 精准匹配流程：只消费已就绪语义资产

### 5.1 查询前置检查

用户输入 1-20 个需求编号时，系统先精确定位记录，去重、大小写不敏感并保持输入顺序。基准记录必须满足：

- 记录可读且存在完整清洗原文；
- 若消费 AI 语义卡片，则其状态必须为 `ready`，且 `contentHash`、`analyzerVersion`、`modelSignature` 与当前环境一致；
- 有效卡片必须通过 schema、UID、逐字段证据、置信度和枚举校验；未就绪或无效卡片不参与结构化增强。

基准为 `pending`、`processing`、`failed` 或签名过期时，查询不得停止，也不得在查询阶段生成卡片或使用规则推断业务语义；应继续使用完整清洗原文，并可明确提示：

> 该需求的 AI 语义卡片尚未就绪，本次将使用完整清洗原文继续全库匹配；结构化语义召回仅使用当前有效的 AI 卡片增强。

候选集合必须覆盖当前 embedding `modelVersion` 有效索引中的全部可读数据中心记录，并排除本次输入的全部基准 UID。Dense、BM25 和 Cross-Encoder 以清洗后完整原文为主输入，不得因候选记录的 AI 语义卡片为 `pending`、`processing`、`failed` 或尚未生成而将其从原文召回路径排除。仅结构化字段召回使用 `ready` 且签名有效的 AI 卡片作为增强信号；候选无有效卡片时使用独立的 `source_only` 原文视图供 Cross-Encoder 和 AI 解释读取，不在查询阶段写入、生成或伪装 AI 语义结果。

### 5.2 混合召回与卡片隔离

混合召回在当前 embedding 索引与有效语义资产快照上运行，三路最多各取 100 条，以 RRF（`k=60`）合并最多 50 条候选：

1. **Dense**：基准和候选的主要输入是完整清洗原文，使用当前有效 embedding 模型和索引；不以推断语义卡片重写或替换原文。
2. **SQLite FTS5/BM25**：主要输入是完整清洗原文及明确原始字段文本；不使用正则推断的动作、对象或状态作为词法事实。
3. **结构化召回**：只使用通过所选质量路由及统一校验的 AI 卡片字段和字段置信度；卡片不合法或未 `ready` 的记录不进入该路。

AI 卡片可作为 Cross-Encoder 的结构化补充输入，也可供最终批量解释模型理解字段语义，但完整清洗原文始终是事实主输入。卡片不能覆盖、改写或替代原文；卡片与原文冲突时以原文为准并使该卡片重新进入失败/待处理流程。Dense/BM25 保留原文召回路径，结构化卡片只承担结构化召回和后续语义增强，避免一个错误卡片污染全部召回路线。不得仅凭卡片分数、关键词分数或 Cross-Encoder 分数直接判定正式匹配。

### 5.3 分阶段候选分析与缓存策略

“候选分阶段分析”是查询阶段对已就绪资产的消费顺序，不是查询时生成卡片：

```text
数据中心当前 embedding 索引 + 资产中心 AI 语义化增强资产
  -> 建立全量原文 Dense/BM25 集合与 ready 有效卡片结构化集合
  -> 三路各取最多 100 条
  -> RRF 合并最多 50 条
  -> 本地 Cross-Encoder 重排前 20 条
  -> 确定性多维评分（Cross-Encoder 55% + 可用的语义/关键词/域/对象/动作维度）
  -> Top 10 一次批量 AI 解释，仅输出相似点、差异和已校验的双方原文证据（证据编号契约另行执行）
  -> UID/证据/schema 校验，解释失败不改变确定性分数
  -> 结构化结论缓存，缓存命中后跳过模型解释
  -> 正式匹配、参考关联、无匹配或候选级隔离
```

候选分阶段规则如下：

- 卡片生成阶段面向资产中心选择的全部记录，效果优先，不因为它们当前是否可能进入某一次查询的前 20 条而跳过分析；
- 召回阶段的结构化增强只消费已经 `ready` 的卡片，Dense/BM25 消费当前索引中的完整原文；查询中不得新增 AI 卡片生成任务；
- Cross-Encoder 输入完整清洗原文，并使用有效卡片作结构化补充；source-only 视图不含推断动作、对象或状态；资源、UID 覆盖或分数异常时失败关闭；
- Cross-Encoder 前 20 条全部完成确定性评分，只有前 10 条进入一次批量 AI 解释；解释模型不得输出或修改关系、分数或匹配层级。
- AI 解释必须覆盖本批次全部候选 UID，并通过相似点、差异和双方原文证据校验；JSON、UID 或证据异常时整批解释不可用，但已完成程序校验的确定性结果仍保留，不重复调用已健康的候选。语义卡片的证据 ID 化不属于本轮实现。
- 解释单次模型调用最多等待 90 秒；在线模型和本地 Ollama 均使用单个有界批量调用，避免按候选逐条调用。解释不可用时标记候选为 `unavailable`，不得把失败解释伪装成已复核结论。

语义卡片缓存是记录级持久化缓存，命中条件见第 3.2 节。匹配结论缓存只保存已经完成“确定性评分 + AI 解释 + 程序校验”的结构化结论，身份包含基准/候选 UID、查询内容哈希、双方原文与卡片哈希、语义分析器与语义模型签名、embedding 与 Cross-Encoder 版本、匹配提示词/schema 策略版本和匹配模型签名。任一记录原文、卡片、模型、提示词或版本变化都必须自动失效。缓存不保存模型原始响应、隐藏思维链或逐 Token 内容；命中后仍重新执行当前查询的召回和重排，只有候选再次进入当前 Top 10 解释集合时才复用结论。

## 6. 关系、综合匹配度与硬规则

| 关系 | 业务判定 | 分数范围 | 输出层级 |
| --- | --- | ---: | --- |
| `duplicate` | 业务目标、功能对象和目标动作基本一致 | 85-100 | 正式匹配 |
| `highly_similar` | 核心目标和对象高度相近，存在有限差异 | 70-94 | 正式匹配 |
| `partial_overlap` | 部分目标、对象或流程重叠 | 40-69 | 参考关联 |
| `same_pattern` | 动作模式相似，但对象或目标不同 | 25-59 | 参考关联 |
| `topic_only` | 仅产品域、模块或主题相同 | 10-39 | 不展示 |
| `unrelated` | 无有效业务关联 | 0-24 | 不展示 |

关系先于分数确定。综合匹配度是程序基于 Cross-Encoder、可用结构化字段和召回信号计算，再经过硬规则校验的业务判断分；AI 只生成相似点、差异和证据解释，不得修改关系或分数，不解释为统计概率或准确率。

硬规则包括：

- 文案修改不等于权限配置或功能新增；
- 功能新增不等于缺陷修复；
- 相同模块不等于相同需求；
- 功能对象相近但目标动作不同，不得判为高度相似；
- 动作相同但功能对象不同，最多判为 `same_pattern`；
- 记录类型差异作为判定特征，不作为候选召回预过滤条件；
- 原文证据优先于卡片摘要，硬规则优先于模型高分；
- 不得为凑数量展示 `topic_only` 或低相关候选。

## 7. 展示契约

每个基准编号展示编号、名称、描述、模块、需求类型、语义卡片状态和匹配结论。基准未 `ready` 时应标明本次使用完整原文完成匹配，不得隐藏已经通过 Cross-Encoder 与确定性评分的候选；Top 10 候选的 AI 解释状态必须单独显示。

每条可见候选展示：

- 需求编号、名称、描述、模块和需求类型；
- 匹配关系和综合匹配度；
- 相同点、主要差异和基准/候选双方逐字原文证据；
- Dense 召回分、BM25 分、结构化召回分、Cross-Encoder 重排分、确定性评分明细和 AI 解释状态；
- 候选语义资产未就绪或签名异常时不得冒充 AI 语义卡片；若其完整原文已通过 Cross-Encoder 与确定性评分，仍可作为原文匹配来源展示。

没有正式匹配时必须返回：

> 未发现业务目标一致的高度相似或重复需求。检索到的记录仅存在主题、模块或操作模式上的关联。

编号不存在、记录不可读、完整清洗原文为空、候选索引为空或关键流程异常时，不写入未经验证的 `sources` 或 `dataViews`，并返回明确原因。基准卡片未就绪本身不是失败条件。

## 8. 自动化验收

自动化验收必须覆盖真实 AI 调用契约和失败路径，不能只用一个直接构造的正则卡片通过测试。

### 8.1 语义卡片质量路由

- standard 健康记录恰好完成一次已验证的结构化抽取，不启动 `independent`/`adjudication`；核心字段失败或低置信时只增加一次定向修复，不能退化为固定三阶段；strict 恰好完成已验证的 `initial` 与独立 `independent`，仅在分歧或低置信时增加 `adjudication`，无分歧且核心字段可信时不得无条件发起第三次调用；
- strict 的 `initial` 与 `independent` 输入均不包含对方结论且可以并行；`adjudication`（触发时）同时收到原文和两份分析的待裁决字段；standard 与 strict 的任务质量模式和 `think` 开关在任务内保持不变，历史 `deepThinking=true` 等价 strict；
- 每个最终字段都有 `value/evidence/confidence`，证据逐字受完整清洗原文支持，置信度在 `0..1`，枚举全部合法；`requirementType`、`productDomain`、`module` 由服务端注入，最终卡片仍必须包含并校验它们；
- 缺 UID、未知/重复 UID、字段遗漏、证据不匹配、置信度非法、枚举非法、schema 错误或路由最终结果不完整时必须进入 `failed`，不得产生 `ready`；
- 使用包含“新增、修改、异常、按钮、支持”等诱导词的回归样本，断言规则不会推断 `action`、`functionalObject`、状态、输入输出、约束或验收，只有通过路由和验证的 AI 输出可以产生这些语义。

### 8.2 状态、缓存与资产中心

- 验证新记录为“待处理”，执行中为“处理中”，成功为“已就绪”，任一失败为“失败”；失败重试能重新进入处理中；
- 验证资产中心可以按四种状态筛选，单条执行和批量执行均产生真实任务并显示结果；
- 验证“全部未语义化”由后台覆盖缺失、失败和三类签名过期记录，排除有效 `ready` 与正在处理记录，并一次性接收全部当前未就绪记录；
- 验证跨记录仍按候选顺序安全处理，不发生跨记录模型调用重叠；standard 健康记录只有一次调用，strict 同一记录的 `initial`/`independent` 可以有两个并行调用，裁决只在分歧或低置信时出现；本轮不把跨记录有界并发写成已交付能力；任务快照完整展示当前记录、阶段、成功/失败/剩余数量、最近明细和单条耗时；
- 验证任务快照按实际路由产生阶段开始/完成、校验失败/定向重试和保存事件；阶段完成事件包含已校验字段、置信度和原文证据；strict 的独立复核分歧及触发的最终裁决可回溯；
- 验证成功和失败记录的审计轨迹均写入 `analysis_trace_json` 并可在记录详情回看，同时不包含原始模型响应、完整请求、隐藏思维链或逐 Token 推理字段；
- 验证暂停在安全阶段边界阻止下一阶段/下一记录，继续后恢复；验证终止不再启动后续记录，保留已完成卡片，并把未完成记录恢复为待处理；
- 验证同一进程内刷新/重新进入资产中心可以读取当前任务快照，且同一时间不能启动第二个活动任务；持久化 job manifest 和跨进程恢复不作为本轮验收项；
- 相同 `recordUid + contentHash + analyzerVersion + modelSignature` 的有效 `ready` 卡片命中缓存时，不再调用当前质量路由模型；
- 修改完整清洗原文/明确字段、分析器版本或模型签名时，自动从 `ready` 变为 `pending`，旧卡片不进入检索；
- 缓存损坏、元数据不一致、卡片校验失败时视为未命中并失败关闭，不复用旧卡片；
- 应用重启或任务中断不会把半成品标记为 `ready`。

### 8.3 查询前置与召回隔离

- 基准为 `pending`、`processing`、`failed` 或过期时，断言查询不调用语义卡片生成、不调用正则生成业务语义，改用完整清洗原文进入 Dense/BM25、Cross-Encoder、确定性评分和一次批量 AI 解释；
- 候选集合包含当前 embedding 索引中的全部可读记录；`ready` 有效卡片参与结构化增强，未语义化候选在查询阶段只使用不持久化的 `source_only` 原文视图，不伪造 AI 语义结果；
- Dense 和 BM25 的主要输入断言为完整清洗原文；结构化召回只读取有效 AI 卡片；Cross-Encoder、确定性评分和批量解释同时读取原文与有效卡片；
- 通过错误卡片、失效卡片和卡片字段冲突样本，验证错误卡片不会污染 Dense/BM25 全部召回，且会被隔离/失效；
- 验证三路各 100、RRF 前 50、Cross-Encoder 前 20、确定性评分覆盖 Top20、批量 AI 解释最多 Top10、解释 UID 全覆盖和排除全部基准 UID。
- 验证 20 条候选通常只需要 1 次批量解释调用；解释失败不丢失确定性结果；相同查询第二次命中持久化结论缓存且模型调用数为 0。
- 验证原文、语义卡片、语义/匹配模型签名、embedding、Cross-Encoder 或策略版本变化均使结论缓存失效；本地模型最多 1 路、在线模型最多 2 路并发。

### 8.4 业务回归与其他边界

保留一组通用 hard-negative 合同夹具；夹具中的编号只用于测试数据，不参与运行时分支：

- `VISSLM-TSIS-889` 必须为 `topic_only`；
- `VISSLM-TSIS-376` 允许 `topic_only` 或 `partial_overlap`；
- `VISSLM-TSIS-613`、`395`、`528` 不得成为正式匹配；
- `VISSLM-TSIS-1837` 为 `same_pattern`；
- 基准不产生正式匹配，并返回无高度相似或重复需求的结论。

固定回归还必须覆盖多编号分组、HTML/实体/脚本/样式/控制字符清洗、明确字段别名读取、standard/strict 路由与条件修复/裁决、缓存命中/失效、状态筛选和批量执行、证据校验、错误失败关闭、无正则语义回退、当前索引版本范围和候选 UID 隔离。

人工标注、双人标注/裁决、Excel 样本包、人工金标准以及依赖人工标签的准确率或召回率门禁必须被测试范围明确排除；测试使用固定业务夹具、模型调用桩、原文证据和程序契约，不把人工标签伪装成验收依据。

## 11. 非目标、风险与验收口径

### 11.1 非目标

- 不在本次目标文档中实现代码、数据库迁移、IPC、UI 或模型调用；
- 不新增人工标注、人工金标、双人标注、人工裁决或 Excel 样本包；
- 不改发布版本号、安装包或发布流程；
- 不改变与本目标无关的知识库、项目管理、数据推送和其他专家流程。

### 11.2 风险

- strict 的双路复核和条件裁决仍会增加部分记录的模型调用、延迟和存储压力，资产中心必须提供批量进度、失败原因和重试；standard 健康路径不得为了省调用而跳过核心字段校验；
- 原文、分析器版本或模型签名变化会造成批量失效和重新生成，需要可观测的待处理数量；
- 即使证据和 schema 合法，模型仍可能产生语义误判，因此原文优先、独立分析、AI 裁决、硬规则和失败关闭必须同时存在；本目标不承诺统计准确率；
- 明确排除人工标签意味着没有人工金标准质量门禁，验收重点是原文可追溯、质量路由契约、缓存正确性、状态边界和错误不可扩散。

### 11.3 最终验收口径

只有当语义卡片已经作为持久化资产完成四状态管理，`ready` 资产的内容哈希/分析器版本/模型签名均有效，单条和批量 AI 生成按所选 standard/strict 路由完成，任务级质量模式和思考配置可审计，所有最终结果均通过证据文本、置信度、schema、UID、枚举和核心字段校验，基准与候选优先消费 ready 有效卡片、未就绪时统一使用完整清洗原文继续匹配，候选原文召回覆盖当前全量索引，查询阶段不会偷偷生成 AI 卡片，候选级隔离和关键流程失败关闭自动回归全部通过时，才可接受本目标。跨记录有界并发、持久化 job manifest/重启恢复、语义证据 ID 化和完整指标平台不属于本轮验收，列入后续阶段；任何按需求编号或关键词写死的特殊分支、用正则生成业务语义、查询时前 20 条临时生成 AI 卡片、旧签名卡片复用或人工标注依赖都视为不通过。
